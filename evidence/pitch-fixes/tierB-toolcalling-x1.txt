=== X1 RE-MEASUREMENT (the headline) ===
Method: fire verifies back to back into ONE server process, cycle the 4 samples, count
survivors before the context-window overflow. RAG on vs RAG off, same post-Tier-B build.

  RAG ON  (GTE resident, embed/verify) run 1: overflow at call 6  -> ceiling 5
  RAG ON  run 2 (MAX=7):                       no overflow in 7   -> ceiling >=7
  RAG OFF (CUSTOS_RAG=off):                     no overflow in 8   -> ceiling >=8

WORKER LIFECYCLE (the mechanism):
  RAG ON  : 1 bare-worker start, 0 teardowns  -> GTE resident keeps "models active" > 0,
            so the QVAC bare worker never dies; the vision model's backend context
            accumulates across verifies -> finite ceiling.
  RAG OFF : 22 bare-worker teardowns          -> with no resident model, model count hits
            zero after each verify, the worker is killed + respawned, vision context RESETS
            -> effectively no ceiling.

ATTRIBUTION (answering the direct question):
  Is the call-3-4 -> call-2 regression attributable to Tier A? YES, mechanistically.
  Tier A keeps GTE resident, which prevents worker teardown, which lets context accumulate.
  Confirmed by RAG-off surviving 8+ (worker tears down and resets each verify).
  Per-completion or per-model-load? Neither exactly: it is per-vision-completion accumulation
  WITHIN a long-lived worker, and the worker only stays alive because a model is resident.
  Remove the resident model -> worker dies between verifies -> no accumulation.

IS IT 1 PER PROCESS?  NO. Ceiling with RAG on is 5-7 (variable), not 1.
  The demo runs RAG on (Hugo #1 needs it visible). You do NOT need to restart between the
  clean invoice and the fraud invoice.
  RESTART RULE (conservative, one below the minimum observed): restart `serve` every 4 verifies.
  The scripted demo is 2 verifies (clean+settle, then fraud) -> a mid-demo restart is OPTIONAL.
