clearStorage DELETES THE MODEL WEIGHTS FROM DISK. It is a cache-eviction flag,
not a context reset. Running this test would have removed Qwen3-VL-2B from the
local model cache and forced a re-download. NOT RUN.

Also note the same file unloads unconditionally:
    if (entry.local.model.unload) { await entry.local.model.unload(); }
    unregisterModel(modelId)
so the model IS being released each cycle regardless of clearStorage.

A single prompt therefore CANNOT overflow 8192 on its own (3x headroom).
Failing calls log an OCR row (blocks=15 / blocks=19 — normal) and then NO

--- H3: cumulative context consumption, ~2780 tok/call  => CONFIRMED ---
Prediction: the overflow point should scale linearly with ctx_size.
  8192  / 2780 = 2.95  -> expect failure on call 3-4
  16384 / 2780 = 5.89  -> expect failure on call 6

Observed, 8 sequential verifies at ctx_size=16384:
  call 1 [ui-clean]      21792ms  VERIFIED
  call 2 [ui-fraud]      23781ms  BLOCKED G3
  call 3 [ui-injection]  23056ms  BLOCKED G0
  call 4 [ui-amount]     21690ms  BLOCKED G2
  call 5 [ui-clean]      24277ms  VERIFIED
  call 6 [ui-fraud]     291138ms  *** ERROR: prompt exceeds the model's context window ***
  call 7 [ui-injection]  25457ms  BLOCKED G0     <- self-clears after the failure
  (call 8 not run — harness timeout)

Baseline at ctx_size=8192 for comparison:
  run A (4 samples): PASS PASS PASS  ERROR(call 4, 110s)
  run B (4 samples): PASS PASS ERROR(call 3, 113s) PASS

The wall moved from call 3-4 to call 6 when the window doubled. Mechanism
confirmed: context is consumed cumulatively across verifies within one server
process, ~2780 tokens per verify, and is not released by the load/unload cycle.
The overflow self-clears — the call after the failure succeeds.

--- IMPORTANT TRADE-OFF ---
Doubling ctx_size buys headroom but makes the eventual failure WORSE:
  ctx 8192  -> fails at call 3-4, hangs ~110s
  ctx 16384 -> fails at call 6,   hangs ~291s (nearly 5 minutes)
